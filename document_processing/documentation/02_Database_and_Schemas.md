# Phase 2: Database and Schemas

To ensure strict data integrity and type safety, Phase 2 implements a rigid boundary between database models (Django ORM) and in-memory data structures (Pydantic).

---

## Pydantic Data Contracts (Schemas)

All inter-service communication utilizes Pydantic v2 schemas with `model_config = ConfigDict(extra='forbid')`. This guarantees that LLM outputs perfectly match our expectations before hitting the database.

### Core Schemas:
- **`OCRPageResult`**: Stores the raw text, word count, character count, and the strategy used to extract it. Also tracks arrays of detected handwriting segments.
- **`PageAnalysisResult`**: A heuristic snapshot used by the router to decide if a page contains tables, stamps, or drawings.
- **`TableResult`**: Defines the JSON structure required from Gemini when parsing Bill of Quantities (BOQ). Crucially, it preserves spatial relationships via the `merged_cells` dict array (tracking rowspans and colspans).
- **`DrawingResult`**: The strict schema for Architectural/Engineering drawings. Enforces the extraction of Revision Histories, Title Blocks, Grid References, and Scale.

---

## Django ORM Models

Data is persisted into PostgreSQL. We heavily leverage PostgreSQL's `JSONField` (JSONB) capability to store the complex, nested outputs generated by the Pydantic schemas.

### 1. `ProcessingJob`
The parent tracker for an entire document's journey.
- **Fields**: `id`, `status` (PENDING, SPLITTING, PROCESSING, COMPLETED, FAILED), `total_pages`, `processed_pages`, `processing_meta` (JSON field tracking costs/strategies).
- **Relationships**: Foreign Key to the Phase 1 `Document` model.

### 2. `Page`
Tracks the execution state of an individual page, enabling granular retries.
- **Fields**: `page_number`, `status` (including `NEEDS_REVIEW`), `strategy_used`, `confidence`, `quality_score`, `error_message`, `refinement_level`, `layers_to_run` (JSON array of executed layers), and multiple boolean flags (`contains_handwriting`, `contains_tables`, etc.).

### 3. `OCRResult`
A One-To-One mapping to the `Page` model. Stores the bulky text data.
- **Fields**: `raw_text` (exactly as the OCR engine saw it), `cleaned_text` (post-ContentCleaner), `handwriting_segments` (JSON array).

### 4. `ExtractedContent`
A polymorphic table storing specialized entities discovered on a page (Tables, Stamps, Drawings, Signatures).
- **Fields**: `content_type` (Enum), `raw_data` (JSONB payload conforming to Pydantic schemas), `text_preview`, `sequence_order`.

---

## The Repository Pattern

Services are forbidden from importing Django models directly. Instead, they instantiate Repositories:
- `ProcessingRepository`
- `PageRepository`
- `ContentRepository`

This ensures that if we ever migrate from Django ORM to SQLAlchemy or raw async drivers, the core business logic (Services) remains untouched. All database operations, including atomic `F()` expression increments for page counts, are localized to these files.
